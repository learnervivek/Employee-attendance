# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` (lines 72–74) | Returns HTTP 200 without verifying MongoDB connectivity. If the database is down or unreachable, health probe falsely indicates readiness. | Shut down MongoDB or point `MONGO_URI` to an unreachable port; `GET /health` continues to return 200 OK instead of 503 Service Unavailable. | Added `client.admin.command('ping')` inside a `try/except` block, returning HTTP 503 if ping fails. |
| 2 | `compute_late_minutes()` (lines 33–37) | Uses `minutes > 10` after integer truncation (`int((punch_in - start).total_seconds() / 60)`). Rule R2 requires late only if punch-in is strictly more than 10:00 (> 600s). For 09:40:01 (shift start 09:30), elapsed seconds is 601, yielding `int(601/60) = 10`. `10 > 10` evaluates to `False`, incorrectly returning 0. | Call `compute_late_minutes` with punch-in at 09:40:01 on shift 09:30; returns 0 instead of 10. | Changed condition to evaluate elapsed seconds strictly greater than 600 (`diff_seconds > 600`), then compute whole minutes as `int(diff_seconds // 60)`. |
| 3 | `compute_late_minutes()` (line 35) | Computes shift start via `punch_in.replace(hour=h, minute=m)`. For overnight shifts (e.g., 22:00–06:00) where punch-in is past midnight (e.g. 01:00 on the day after shift started), replacing the hour sets the start to 22:00 of that same day (21 hours in future), resulting in negative minutes. | Punch-in at 00:30 on July 7 for a 22:00–06:00 shift yields negative difference and returns 0 late minutes instead of 150. | Anchor the shift start datetime to the record's attendance date (`attendance_date`), resolving overnight dates correctly per R1. |
| 4 | `compute_work_hours()` (lines 40–41) | Uses Python built-in float `round((punch_out - punch_in).total_seconds() / 3600, 2)`. Python `round()` performs round-half-to-even (banker's rounding), whereas Rule R4 explicitly specifies rounding to 2 decimals half-up. | A duration of 9630 seconds (2.675 hours) rounds to 2.67 under banker's rounding instead of 2.68. | Implemented rounding via `Decimal(diff_sec) / Decimal(3600)` with `.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)`. Also truncated timestamps to whole seconds per R1. |
| 5 | `compute_overtime()` (lines 44–47) | Returns `max(0, int((punch_out - end).total_seconds() / 60))` without enforcing the 30-minute minimum threshold. Rule R3 mandates overtime is counted only if at least 30 minutes; otherwise 0. | Punching out 15 minutes past shift end records 15 minutes of overtime instead of 0. | Added threshold check: return `mins` only if `mins >= 30`, otherwise return 0. |
| 6 | `compute_overtime()` (line 46) | Computes shift end on `date_str` without accounting for overnight shifts. For overnight shifts (`shift_end <= shift_start`), the shift ends on the next calendar day (`date_str + 1 day`). Also mixes timezone-aware `end` with potentially naive `punch_out`. | Punch-out at 06:40 on July 7 for a 22:00–06:00 shift on July 6 compares against 06:00 on July 6 (16 hours prior), yielding > 24h overtime or raising offset-naive vs offset-aware `TypeError`. | Added 1 day to `base_date` when `shift_end <= shift_start` and ensured both operands are aware UTC/IST datetimes. |
| 7 | `create_employee()` (lines 77–86) | Relies on check-then-insert (`db.employees.find_one(...)`). Under concurrent creation requests with the same `emp_code`, both pass the check and attempt insertion, causing race conditions and unhandled 500 errors. | Sending simultaneous `POST /employees` requests with identical `emp_code` results in unhandled `DuplicateKeyError` (500 Internal Server Error) or duplicate documents. | Created a unique index on `emp_code` at startup and caught `pymongo.errors.DuplicateKeyError` to return HTTP 409 Conflict. |
| 8 | `create_employee()` & `EmployeeIn` (lines 53–61, 82) | Sets `created_at = datetime.now()` (naive local time) and returns it unformatted. OpenAPI specification requires `created_at` as integer epoch milliseconds. Lacks validation for email, `emp_code` format (`^EMP\d{4,6}$`), and rule that `shift_start != shift_end`. | Sending `shift_start="09:00"` and `shift_end="09:00"` returns 201 instead of 422; response contains datetime string instead of integer epoch ms. | Added Pydantic regex validators, validated `shift_start != shift_end`, and serialized `created_at` as epoch milliseconds integer. |
| 9 | `list_employees()` (line 93) | Calculates pagination offset as `skip = page * page_size`. Since `page` is 1-indexed (starts at 1), `page=1` with `page_size=20` sets `skip=20`, completely skipping the first 20 employees. | `GET /employees?page=1&page_size=20` returns employees 21 to 40 instead of employees 1 to 20. | Fixed offset calculation to `skip = (page - 1) * page_size`. |
| 10 | `list_employees()` (line 94) | Computes `total = db.employees.count_documents({})`, which ignores the active `department` filter. Rule R10 requires `total` to reflect applied filters. | `GET /employees?department=Sales` reports total count of all employees in company rather than count of Sales department employees. | Changed total count to `total = db.employees.count_documents(q)`. |
| 11 | `list_employees()` (line 95) | Does not apply sorting to the query cursor. OpenAPI specification requires employees to be sorted by `emp_code` ascending. | Returned employee order is non-deterministic (natural MongoDB storage order). | Added `.sort([("emp_code", 1)])` to cursor query. |
| 12 | `punch_in()` (lines 100–122) | Missing validation for non-existent employees. If `db.employees.find_one()` returns `None`, line 113 throws `TypeError: 'NoneType' object is not subscriptable` resulting in an unhandled 500 Internal Server Error instead of 404. | `POST /attendance/punch-in` with `emp_code="EMP9999"` returns 500 Internal Server Error. | Added check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 13 | `punch_in()` (lines 104–118) | Check-then-insert race condition on attendance date. If two identical punch-in requests arrive simultaneously, both find no existing record and both attempt insert. Without unique compound index and conflict handling, duplicate logs are created or unhandled 500 errors occur. | Sending simultaneous punch-ins for the same employee and day creates duplicates or crashes with 500. | Created unique compound index on `("emp_code", 1), ("date", 1)` at startup, wrapped insertion in try/except for `DuplicateKeyError`, and returned HTTP 409 Conflict. |
| 14 | `punch_in()` (lines 102–103) | Attendance date calculation uses server local time `ts.date().isoformat()` and ignores overnight shift rules (R1). An overnight shift punch-in before `shift_end` belongs to previous day's shift. | Punch-in at 01:00 on July 7 for a 22:00–06:00 shift sets date to `2026-07-07` instead of `2026-07-06`. | Implemented `get_attendance_date()` converting timestamp to IST and subtracting one day if shift is overnight and time is strictly before `shift_end`. |
| 15 | `punch_in()` & `list_attendance()` (lines 119, 149) | Injects an `id` field (`doc["id"] = str(res.inserted_id)`). OpenAPI and DATA_MODEL.md strictly state: "Attendance records have no id either; a record is addressed by (emp_code, date). _id is internal and never appears in a request or response." | Response JSON contains `"id": "..."`, which violates `AttendanceRecord` schema. | Removed `_id` and prevented setting any `id` attribute in the returned record. |
| 16 | `list_attendance()` (lines 144–147) | Fetches the entire collection into memory via `list(db.attendance_logs.find(q))`, sorts in Python with `list.sort(key=...)`, and slices in memory. At 100,000+ documents this exhausts RAM, spikes latency, and crashes. | Loading 100k records causes extreme memory usage and request timeouts. | Offloaded filtering, sorting, and pagination directly to MongoDB: `find(q).sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`. |
| 17 | `list_attendance()` (line 145) | Sorts only by `date` descending. OpenAPI specifies: "Sorted by date descending, then emp_code ascending." | Records with the same date are returned in non-deterministic order. | Added compound sort order `[("date", -1), ("emp_code", 1)]`. |
| 18 | `list_attendance()` (lines 136–141) | Fails to validate date range parameters. Contract explicitly mandates: "`date_from` > `date_to` -> 422". | `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` returns 200 OK with empty items instead of 422 Unprocessable Entity. | Added validation check: `if date_from and date_to and date_from > date_to: raise HTTPException(422, "date_from must not be greater than date_to")`. |
| 19 | Setup & Lifecycle (lines 22–24) | `MongoClient` initialized without `tz_aware=True`, and no indexes are created at startup. Un-indexed collections cause full collection scans (`COLLSCAN`) across all endpoints. | MongoDB returns naive datetimes causing timezone calculation bugs; MongoDB explain plans show `COLLSCAN` on all queries. | Instantiated `MongoClient` with `tz_aware=True` and implemented startup index creation for all required queries in FastAPI `lifespan`. |

### Non-defects examined and retained
1. **Plain string format for dates (`YYYY-MM-DD`) and times (`HH:MM`)**:
   We examined storing calendar dates and shift times as strings vs BSON dates. As explicitly explained in `DATA_MODEL.md`, a calendar date is not an instant and turning it into one forces a timezone onto it. Retaining ISO string representations for `date`, `joined_on`, `shift_start`, and `shift_end` is intentional and preserves timezone semantics.
2. **Exclusion of `ABSENT` / `LEAVE` creation from punch endpoints**:
   We verified whether punch endpoints should create `ABSENT` or `LEAVE` records. Per the problem statement and DATA_MODEL.md, punch-in/out only creates and manages presence statuses (`PRESENT`, `WFH`, `ON_DUTY`). `ABSENT` and `LEAVE` records are back-office seeded or created via manual regularization (`PATCH`), so omitting them from `POST /attendance/punch-in` is by design.
3. **Empty history on punch-in / punch-out**:
   We examined whether initial punch events should append to `history`. DATA_MODEL.md and OpenAPI confirm that `history` is reserved solely as an audit trail for manual corrections (regularizations). Punch-in and punch-out are original events and must have `history: []`.
